# PPE Tracker — контекст проекта

Документ для продолжения работы на любой машине и с любым ассистентом.
Описывает архитектуру, принятые решения и известные ловушки — то, чего не
видно в коде с первого взгляда.

---

## Правило обновления — читать до начала работы

**Этот файл ведётся вместе с кодом, а не «потом».** Изменение, которое
затрагивает архитектуру, схему данных или открывает новую ловушку, должно
дополнять PROJECT.md **в том же коммите**. Иначе контекст теряется, и
следующий человек (или ассистент) наступит на ту же грабли.

Критерий, что писать:

| Писать | Не писать |
|---|---|
| Новое архитектурное решение и его причина | «добавил кнопку», «поправил стиль» |
| Ловушка, которая уже ломала проект, и как её распознать | описание текущей задачи |
| Изменение схемы данных, новая миграция | детали, которые видны в коде |
| Правило, которое легко нарушить незаметно | то, что устареет через месяц |

Проверка перед коммитом: если изменение удивит того, кто откроет проект
через полгода — оно должно быть здесь.

## Что это

Учёт средств индивидуальной защиты (СИЗ) на предприятии: справочники,
сотрудники, нормы выдачи, фактические выдачи со сроками носки.

**Стек:** FastAPI + SQLAlchemy 2.0 (async, asyncpg) + PostgreSQL + Alembic.
Фронтенд — Jinja2-шаблоны, Bootstrap 5.3 с CDN, обычный JS без сборщика.

**Запуск:** Docker Compose (api + db), код монтируется в контейнер,
uvicorn с `--reload`.

## Предметная область

```
Department (дерево) → Position → PositionPpeNorm → PpeItem
Employee → EmployeePpeSize (размеры по группам)
Employee → EmployeePpeIssue (выдачи)
PpeItem → PpeFunction, PpeSizeGroup, Unit
PpeSizeGroup → PpeSize (значения размеров)
```

- **Норма** — сколько и на какой срок положено должности.
- **Выдача** — что фактически выдано сотруднику, со сроком годности,
  рассчитанным из нормы.
- **Размер сотрудника** — по одной записи на размерную группу
  (`uq_employee_size_group`).

## Ключевые решения

### Авторизация и CSRF

- Сессия через `SessionMiddleware`, cookie `ppe_session`.
- `SECRET_KEY` обязателен, приложение падает на старте без него — сделано
  осознанно вместо тихого дефолта.
- CSRF — double-submit: токен в сессии и в `<meta name="csrf-token">`,
  клиент шлёт его в `X-CSRF-Token` для POST/PUT/PATCH/DELETE.
- **Порядок зависимостей важен:** `require_csrf` подключён раньше
  `get_current_active_user`, чтобы отклонённый запрос не открывал
  соединение с БД. Следствие: неавторизованный небезопасный запрос
  возвращает 403, а не 401.

### Пагинация

`GET /api/v1/<список>/` принимает `page`, `page_size`, `search` и флаг
`paginated`.

**Флаг обязателен:** без `paginated=true` эндпоинт отдаёт **обычный
массив**. Это нужно выпадающим спискам, которым требуются все значения
сразу (выбор подразделения, должности, СИЗ).

С `paginated=true` — конверт `{items, total, page, page_size, pages}`.

Сортировка всегда явная. Без `ORDER BY` Postgres вправе менять порядок
между запросами, и при `LIMIT/OFFSET` это даёт дубли и пропуски на
границах страниц.

### Несколько норм на пару «должность + СИЗ»

Ограничение `uq_position_ppe_item` **снято** миграцией `a9f3c06b2d18`.
Причина: в матрице норм Минтруда у одной пары есть основное наименование
и до четырёх альтернатив.

При выдаче берётся **первая по id** норма пары. В коде поэтому стоит
`scalars().first()`, а не `scalar_one_or_none()` — последний при дублях
бросает `MultipleResultsFound` и даёт 500.

### Вкладки — обычные страницы, не iframe

Раньше вкладки были iframe: модалки открывались внутри рамки (backdrop
накрывал только таблицу), прокрутка была двойной. Теперь у каждой вкладки
свой URL: `/ppe-items`, `/norms`, `/ppe-functions`, `/ppe-size-groups`,
`/units`, `/departments`, `/positions`.

`/ppe` и `/structure` — редиректы на первые вкладки.

### Модалки вместо страниц редактирования

Справочники и сотрудник редактируются в модалках. Страница
`/employees/{id}/edit` — редирект на список.

У модалки создания и редактирования один и тот же DOM: переключаются
заголовок, текст кнопки и скрытое поле `version`.

### Дизайн-система

Всё в `app/static/css/app.css`. Токены: `--brand` (#5b2c8a, фиолетовый —
действия и заголовки), `--accent` (#ff6600, оранжевый — удаление и отмена),
радиусы, тени, отступы `--space-*`.

**Правила:** никаких inline-стилей, никаких `!important`.
Иконки: `.btn-icon` фиолетовая, `.btn-icon--danger` оранжевая.
Бейджи: только `badge-purple` и `badge-orange`.

Списки: `.data-table--dense` (отступ ячейки 6px), 20 строк на страницу.

## Известные ловушки

Каждая из них уже приводила к поломке. Проверять при изменениях
соответствующего кода.

### 1. asyncpg и типы параметров в миграциях

Один параметр, использованный и в `SELECT`, и в сравнении с колонкой,
даёт `inconsistent types deduced` — драйвер не может вывести тип.

```sql
-- плохо: $2 встречается как text и как varchar(50)
INSERT ... SELECT :value ... WHERE size_value = :value

-- хорошо: явное приведение
WHERE size_value = CAST(:value AS varchar(50))
```

**`NULL` в `CAST` тоже ломается.** Для `gender IS NULL` нужна отдельная
ветка SQL без приведения.

### 2. MissingGreenlet

Pydantic при сериализации обходит всю схему и читает **все** поля. Если
`relationship` не загружен через `selectinload`, SQLAlchemy пытается
подгрузить его лениво — в async это невозможно.

**Правило:** набор `selectinload` должен покрывать всю вложенную схему
ответа. Например, `PpeItemRead` включает `function`, `size_group` и
`unit` — все три обязательны в опциях загрузки.

### 3. Порядок в шаблоне: модалка раньше скрипта

Скрипт страницы выполняется в момент подключения. Модалка, объявленная
**после** `<script>`, для него не существует: `getElementById` вернёт
`null`, обработчик упадёт.

Модалки — в блоке `content`, скрипты — в `scripts`.

### 4. Двойной триггер модалки

`data-bs-toggle="modal"` **и** `openCreateModal()` одновременно —
Bootstrap создаёт второй backdrop на каждый клик, экран темнеет слоями.

У кнопок, которые открывает скрипт, не должно быть `data-bs-toggle`.

### 5. Расхождение id между шаблоном и JS

`getElementById('create-form')`, когда форма имеет `id="employee-form"` —
тихий `null` и неработающая кнопка.

### 6. Сроки носки

`app/utils/dates.py`, `add_wear_period` на `relativedelta`. Значения
`wear_period_value` + `wear_period_unit` (`год`, `месяц`, `до износа`).

Для «до износа» срок не считается — `expiry_date` остаётся пустым.

### 7. BOM в сообщении коммита

`Set-Content -Encoding UTF8` в PowerShell 5.1 пишет BOM, а git переносит
его в сообщение как обычный символ: тема коммита начинается с невидимого
`U+FEFF`. Так испорчены `65cef95` и `62938c6` — выглядят нормально,
но первый байт темы не тот, и поиск по префиксу сообщения не находит их.

Текст для `commit -F` писать только без BOM:

```powershell
[System.IO.File]::WriteAllText($tmp, $Message, (New-Object System.Text.UTF8Encoding($false)))
```

Тот же приём обязателен для файла кеша в `push-ppe.ps1`: с BOM первый
символ пути не совпадает, и сохранённый путь перестаёт находиться.

## Миграции и данные

Всегда проверять `alembic upgrade head` перед работой с интерфейсом:
отсутствующая колонка даёт 500 на списках, причём не всегда на том,
который её использует напрямую (через цепочку join).

Размеры одежды и обуви — в миграциях `b7e1c93d5a24`, `d5a8f21c4e37`,
`e2c74b81f9d6`.

**Обувь в штихмассовой системе** (37–48). На самой обуви маркировка может
отличаться (валяная 24–35, боты 300–345) — соответствие в описании группы.

## Git

Remote: `https://github.com/Death-Router/ppe-tracker` (ветка `main`).

**Push с машины разработки требует токена** — SSH не проходит через
локальный прокси/VPN. Personal access token с галочкой `repo`.

Токен сохраняется **на каждой машине отдельно** — Windows Credential
Manager не переносится, запись `git:https://github.com` (пользователь
`Death-Router`) появляется после первого входа через окно GCM. На work
это уже сделано и проверено 4 ноября 2026 реальной записью в GitHub,
а не только сухим прогоном.

Скрипт push и токен — независимые вещи: `push-ppe.ps1` лежит рядом
с проектом, а не в нём, поэтому правки в скрипте **не разъезжаются
через git**. На второй машине его нужно править отдельно.

Сообщения коммитов — по-русски, через файл:
`git -c i18n.commitEncoding=UTF-8 commit -F message.txt`.

Формат: тип(область), затем зачем изменение, а не только что именно.
Причины важнее деталей — они восстанавливают контекст.

## Рабочая среда: home и work

Две машины, роли разделены. В переписке и документах называются так:

| Имя | Путь | Роль |
|---|---|---|
| **home** | `C:\projects\ppe-tracker` | правки кода, git, commit, push |
| **work** | `C:\projects\ppe-tracker` | то же плюс запуск: Docker в WSL, `.env`, БД, браузер |

**Клон лежит по одному и тому же пути на обеих машинах**, поэтому все
пути в этом документе к машине не привязаны. Правки можно делать на
любой — они сходятся через GitHub: `push` на одной, `git pull` на другой.
Раньше здесь было «home — код, work — только запуск»; на деле сессия
ассистента бывает и на work, и правки оттуда уходят так же.

**Где что выполняется:**

- **home** — только код и git. Ни `docker compose`, ни `alembic`: на этой
  машине нет ни Docker, ни `.env`, ни базы. Сюда `.env` и не нужен — он
  в `.gitignore` и живёт только на work.
- **work** — и код, и всё, что связано с запуском: `docker compose up`,
  `alembic upgrade head`, проверка в браузере. Docker берётся из
  Docker Desktop в WSL, с ним работают вручную через VS Code.

**Цикл работы:**

1. Правки на той машине, где удобно, затем из `C:\projects` —
   `.\push-ppe.ps1` (или двойной клик по `push-ppe.cmd`).
2. На второй машине: `git pull`, а на work при необходимости
   `docker compose restart api` и `alembic upgrade head`.

### Скрипт push живёт вне репозитория

`push-ppe.ps1` и `push-ppe.cmd` лежат **в `C:\projects`, на уровень выше
папки проекта**, и в репозиторий не входят. Так сделано намеренно: скрипт
сам находит клон рядом с собой (`<папка скрипта>\ppe-tracker`), поэтому
после перезагрузки путь вспоминать не нужно.

- Запускать из `C:\projects`: `.\push-ppe.ps1`. Из корня репозитория
  путь не найдётся — там скрипта нет.
- Скрипт вызывает `git` без полного пути, ему нужен
  `C:\Program Files\Git\cmd` в `PATH` (в машинном `PATH` он есть).
- `push-ppe.cmd` — обёртка для двойного клика: запускает `.ps1`
  с `-ExecutionPolicy Bypass`, поэтому политика сценариев не мешает.
- Сообщение коммита скрипт передаёт через временный файл и
  `-c i18n.commitEncoding=UTF-8`: многострочный текст с кириллицей
  ломается в аргументе командной строки.
- **На каждой машине своя копия скрипта**, и git их не синхронизирует:
  скрипт лежит вне репозитория. Правка, сделанная на одной машине, на
  другой не появится — повторять вручную. Так и вышло с BOM: на work
  исправлено, на home копия осталась с прежним `Set-Content`.

### Если git запускает ассистент

Ограниченная среда, в которой ассистент выполняет команды, может мешать
сильнее обычной консоли. Проверено на work 4 ноября 2026:

- `git` может отсутствовать в `PATH` процесса → вызывать по полному пути
  `C:\Program Files\Git\cmd\git.exe`.
- Штатный TLS-бэкенд `schannel` падает с `SEC_E_NO_CREDENTIALS` →
  `git -c http.sslBackend=openssl ...`.
- Сохранённые креды недоступны: помощник не запускается
  (`sh.exe: couldn't create signal pipe`), поэтому push требует разового
  расширения прав на команду. Анонимный `ls-remote` к публичному
  репозиторию работает и без этого.
- Токен с правом `repo` сохраняется через окно входа GCM как запись
  `git:https://github.com`; повторно вводить его не нужно. Проверено:
  push в GitHub проходит.

**Репозиторий вне OneDrive — намеренно.** Раньше он лежал в синхронизируемой
папке, и `.git` мог попасть в момент записи: это даёт битые объекты и
конфликтные копии вроде `index (1).lock`. Резервная копия и синхронизация —
на GitHub, OneDrive для этого не нужен.
