# PPE Tracker — контекст проекта

Документ для продолжения работы на любой машине и с любым ассистентом.
Описывает архитектуру, принятые решения и известные ловушки — то, чего не
видно в коде с первого взгляда.

---

## Правило обновления — читать до начала работы

**Этот файл ведётся вместе с кодом, а не «потом».** Изменение, которое
затрагивает архитектуру, схему данных или открывает новую ловушку, должно
дополнять PROJECT.md **в том же коммите**. Иначе контекст теряется, и
следующий человек (или ассистент) наступит на ту же грабли.

Критерий, что писать:

| Писать | Не писать |
|---|---|
| Новое архитектурное решение и его причина | «добавил кнопку», «поправил стиль» |
| Ловушка, которая уже ломала проект, и как её распознать | описание текущей задачи |
| Изменение схемы данных, новая миграция | детали, которые видны в коде |
| Правило, которое легко нарушить незаметно | то, что устареет через месяц |

Проверка перед коммитом: если изменение удивит того, кто откроет проект
через полгода — оно должно быть здесь.

## Что это

Учёт средств индивидуальной защиты (СИЗ) на предприятии: справочники,
сотрудники, нормы выдачи, фактические выдачи со сроками носки.

**Стек:** FastAPI + SQLAlchemy 2.0 (async, asyncpg) + PostgreSQL + Alembic.
Фронтенд — Jinja2-шаблоны, Bootstrap 5.3 с CDN, обычный JS без сборщика.

**Запуск:** Docker Compose (api + db), код монтируется в контейнер,
uvicorn с `--reload`.

## Предметная область

```
Department (дерево) → Position → PositionPpeNorm → PpeItem
Employee → EmployeePpeSize (размеры по группам)
Employee → EmployeePpeIssue (выдачи)
PpeItem → PpeFunction, PpeSizeGroup, Unit
PpeSizeGroup → PpeSize (значения размеров)
```

- **Норма** — сколько и на какой срок положено должности.
- **Выдача** — что фактически выдано сотруднику, со сроком годности,
  рассчитанным из нормы.
- **Размер сотрудника** — по одной записи на размерную группу
  (`uq_employee_size_group`).

## Ключевые решения

### Авторизация и CSRF

- Сессия через `SessionMiddleware`, cookie `ppe_session`.
- `SECRET_KEY` обязателен, приложение падает на старте без него — сделано
  осознанно вместо тихого дефолта.
- CSRF — double-submit: токен в сессии и в `<meta name="csrf-token">`,
  клиент шлёт его в `X-CSRF-Token` для POST/PUT/PATCH/DELETE.
- **Порядок зависимостей важен:** `require_csrf` подключён раньше
  `get_current_active_user`, чтобы отклонённый запрос не открывал
  соединение с БД. Следствие: неавторизованный небезопасный запрос
  возвращает 403, а не 401.

### Пагинация

`GET /api/v1/<список>/` принимает `page`, `page_size`, `search` и флаг
`paginated`.

**Флаг обязателен:** без `paginated=true` эндпоинт отдаёт **обычный
массив**. Это нужно выпадающим спискам, которым требуются все значения
сразу (выбор подразделения, должности, СИЗ).

С `paginated=true` — конверт `{items, total, page, page_size, pages}`.

Сортировка всегда явная. Без `ORDER BY` Postgres вправе менять порядок
между запросами, и при `LIMIT/OFFSET` это даёт дубли и пропуски на
границах страниц.

### Несколько норм на пару «должность + СИЗ»

Ограничение `uq_position_ppe_item` **снято** миграцией `a9f3c06b2d18`.
Причина: в матрице норм Минтруда у одной пары есть основное наименование
и до четырёх альтернатив.

При выдаче берётся **первая по id** норма пары. В коде поэтому стоит
`scalars().first()`, а не `scalar_one_or_none()` — последний при дублях
бросает `MultipleResultsFound` и даёт 500.

**В модели ограничения тоже нет** — в `PositionPpeNorm.__table_args__`
остался только `Index("ix_position_ppe_norms_position_item")`. Если вернуть
`UniqueConstraint`, `alembic revision --autogenerate` попытается
восстановить ограничение и упадёт на базе, где альтернативы уже есть.

Следствие: **нигде не сравниваем нормы по одной паре.** Копирование норм
(`POST /position_ppe_norms/copy`) считает дублем только полное совпадение
(СИЗ + срок носки + количество) и копирует альтернативы. Импорт норм
обновляет первую по id норму пары, а не падает с `MultipleResultsFound`.

### Выдача СИЗ: размер списком, количество из нормы

Модалка выдачи (`#issueModal` в `templates/employees/list.html`, логика в
`static/js/employees_list.js`) заполняется сама — иначе выдача
превращалась в переписывание справочников руками:

- **Наименование** — только СИЗ из норм должности сотрудника. Список всех
  СИЗ позволял выдать что угодно мимо нормы.
- **Размер** — `select` из справочника размеров той размерной группы,
  которая задана у СИЗ (`/api/v1/ppe_sizes/?size_group_id=...`), с фильтром
  по полу сотрудника (размер без пола подходит обоим). Предвыбран размер
  из карточки — вкладка «Размеры СИЗ». Раньше это было поле ввода: значения
  вроде «58 размер» не совпадали ни с карточкой, ни со справочником.
- **Количество** — подставляется из нормы выдачи должности.

Размер из карточки, которого нет в справочнике, остаётся в списке отдельным
вариантом с пометкой «из карточки»: иначе подстановка молча терялась и
вместо своего размера сотрудник получал чужой из начала списка.

При расхождении размера с карточкой или количества с нормой показывается
предупреждение (`#issue-warning`), **но выдача не блокируется**:
обоснованное отклонение от нормы бывает нужным, а молчаливая запись
«чего-нибудь» — ошибка учёта.

**Количество сравниваем по первому числу**, а не строкой: в нормах
встречается «1 пара» и «2 комплекта», а в выдаче — «1». Строгое равенство
давало ложные предупреждения на каждом шаге. Если чисел нет вовсе,
сравниваем строки целиком (`firstNumber` в `employees_list.js`).

Срок носки по-прежнему считает сервер: клиент только подставляет поля.

### Поля личной карточки учёта СИЗ (приложение № 4)

Форма — `Личная карточка учета СО и СИЗ РТК 2025.docx` в корне проекта:
приложение № 4 к Положению об обеспечении СИЗ ПАО «Ростелеком» (редакция 2,
приказ 01/01/4523/24 от 13.02.2025). Лист A4 альбомный, таблицы без рамок,
примечания к форме лежат в `word/comments.xml` (в Word это комментарии).

Под графы формы в модели появились поля (миграция `c4d9e2b71f30`):

| Графа карточки | Где хранится |
|---|---|
| Номер карточки (лицевая сторона) | `employees.personal_card_number` |
| Размер: одежды, обуви, головного убора, СИЗОД, СИЗ рук | `employee_ppe_sizes` по размерным группам; группа **СИЗОД** добавлена миграцией |
| Модель, марка, артикул, класс защиты (графа 2 оборота) | `ppe_items.model`, `ppe_items.protection_class` |
| Пункт Норм (лицевая сторона) | `position_ppe_norms.typical_norm_id` → справочник `typical_norms` |
| лично/дозатор (графа 5, сноска `<*>`) | `employee_ppe_issues.issue_method` |
| Возвращено: дата, количество (графы 7-8) | `returned_date`, `returned_quantity` |
| Акт списания: дата, номер (графа 10) | `write_off_act_date`, `write_off_act_number` |

**Рост — из сетки, а не свободным вводом.** Сетка (158-164, 170-176,
182-188, 194-200, 206-212) задана в `app/core/constants.py` и передаётся в
шаблон: список значений в форме и серверная проверка не могут разойтись.
Примечание к форме говорит прямо: «межразмерность будет считаться ошибкой»,
поэтому значение вне сетки отклоняется с 400 и перечнем допустимых. Старые
записи («180», «170») остаются в базе как есть, в форме показываются
отдельным пунктом «вне сетки» — сохранить сотрудника, не выбрав рост из
сетки, нельзя. Это сознательно: печатать карточку с межразмерностью хуже,
чем заставить исправить.

**«лично/дозатор» только для дерматологических СИЗ** — у остальных в
карточке эта графа не заполняется, поэтому поле в модалке выдачи скрыто и в
запрос уходит `null`. Признак берётся из функции СИЗ
(«Дерматологические СИЗ»), отдельного флага в модели нет.

**Возврат и акт — только парой.** `PUT /employee_ppe_issues/{id}` принимает
дату и количество возврата, дату и номер акта, а также способ выдачи.
Дату выдачи, размер и количество менять нельзя: это факт выдачи, он уже
отражён в карточке, поэтому правка возможна только через удаление и новую
запись. Неполные пары (дата без количества, номер акта без даты) отклоняются
с 400 — в карточке такие поля не читаются.

**Остаток не уходит в минус.** Остаток = выдано − возвращено, поэтому
сервер разбирает оба количества как числа (`parse_quantity` в
`employee_ppe_issues.py`) и требует `0 < возвращено ≤ выдано`. Иначе 400 с
точным текстом: «Возврат больше выдачи: выдано 2, возвращают 6. Остаток не
может быть отрицательным». Нечисловое количество («2 пары») тоже отклоняется:
по такой записи остаток не посчитать. Та же проверка стоит при создании
выдачи, если возврат передан сразу. В модалке возврата подсказка показывает
«выдано · остаток» и обновляется при вводе, а клиентская проверка не даёт
отправить заведомо неверное значение.

Отдельной колонки «Возвращено, акт» в таблице выдач больше нет — она
занимала пол-экрана. Статус возврата и акта виден в подсказке кнопки
возврата, сами поля правятся в модалке.

**Количество — только цифры, не больше трёх.** Поля «Количество» при выдаче,
«Возвращено, количество», количество и срок в нормах размечены
`maxlength="3" inputmode="numeric" pattern="[0-9]{1,3}"` (проверка нативная,
через `form.checkValidity()`), а ввод дополнительно чистится маской
`FormHelper.onlyDigits(input, 3)` из `js/common/form.js`: минус, запятая и
буквы отбрасываются на лету, при вставке и при потере фокуса. Без этого «-5»
и «2,5» попадали в строковое поле и ломали остаток.

Разбор количества и правило остатка живут в `js/common/quantity.js`
(`Quantity.parse`, `Quantity.describeReturn`) — их использует и подсказка в
модалке, и предотправная проверка, поэтому тексты не расходятся. Модуль
проверяется без браузера: `js/common/*.js` исполняется в V8 (`mini-racer`),
кейсы — «-5», «6» при выдаче 1, «0», «abc», пусто, «2 пары».

**Номер карточки уникален** (`uq_employees_personal_card_number`). Пустая
строка приводится к `NULL` валидатором схемы: в Postgres `NULL`-ы уникальность
не нарушают, а два `''` — нарушают, и второй сотрудник без номера падал бы
на ограничении.

### Справочник типовых отраслевых норм

`typical_norms` — пункт приложения к Положению и его описание
(`clause`, `description`). Заведён ради графы «Пункт Норм» личной карточки:
раньше её негде было хранить, в форме оставался только общий текст
«Приложение №1 к Положению…».

- Справочник — **отдельная вкладка** раздела «Нормы выдачи» (`/typical-norms`,
  макрос `norms_tabs` в `_tabs.html`), как остальные справочники в «СИЗ» и
  «Структуре». Сначала он висел модалкой на странице норм — раздел выпадал из
  общей схемы: у всех прочих справочников есть своя вкладка с таблицей, поиском
  и модалкой создания.
- Кнопка «Скопировать нормы» осталась на первой вкладке: она про нормы
  должностей, а не про справочник пунктов.
- В норме выдачи пункт выбирается выпадающим списком (`typical_norm_id`).
  Пустой список означает `null` — графа в карточке останется пустой.
- `clause` уникален: пункт вписывают в документ, два разных описания у одного
  номера — это ошибка ввода.
- Связь `ON DELETE RESTRICT` + проверка в API: пункт, на который ссылаются
  нормы, удалить нельзя («сначала уберите его оттуда»). Молча обнулять ссылку
  нельзя — в карточке пропадёт основание выдачи.
- Копирование норм переносит пункт вместе с нормой.

**Сортировка — по номеру, а не по строке.** Пункт записан как «п. 4» или
«п. 12», поэтому номер вытаскивается `substring(clause, '[0-9]+')`, а не
`regexp_replace('[^0-9].*$')` как у размеров: строка начинается с буквы, и
замена от первого нецифрового символа стирала её целиком — все пункты
становились `NULL` и сортировались как строки («п. 12» перед «п. 4»).



Раньше вкладки были iframe: модалки открывались внутри рамки (backdrop
накрывал только таблицу), прокрутка была двойной. Теперь у каждой вкладки
свой URL: `/ppe-items`, `/norms`, `/typical-norms`, `/ppe-functions`,
`/ppe-size-groups`, `/units`, `/departments`, `/positions`.

Вкладки рисует макрос из `_tabs.html`: `ppe_tabs`, `norms_tabs`,
`structure_tabs`. Новый справочник добавляется страницей и пунктом в макросе,
а не модалкой на чужой странице.

`/ppe` и `/structure` — редиректы на первые вкладки.

### Модалки вместо страниц редактирования

Справочники и сотрудник редактируются в модалках. Страница
`/employees/{id}/edit` — редирект на список.

У модалки создания и редактирования один и тот же DOM: переключаются
заголовок, текст кнопки и скрытое поле `version`.

### Дизайн-система

Всё в `app/static/css/app.css`. Токены: `--brand` (#5b2c8a, фиолетовый —
действия и заголовки), `--accent` (#ff6600, оранжевый — удаление и отмена),
радиусы, тени, отступы `--space-*`.

**Правила:** никаких inline-стилей, никаких `!important`.
Иконки: `.btn-icon` фиолетовая, `.btn-icon--danger` оранжевая.
Бейджи: только `badge-purple` и `badge-orange`.

Списки: `.data-table--dense` (отступ ячейки 6px), 20 строк на страницу.

### Обновление в реальном времени (WebSocket)

`/ws/employees/{id}` — канал уведомлений, требует сессии (без неё `close(1008)`).
Клиент (`js/common/ws.js`) подключается к каналу `0` и раздаёт события
подписчикам через `WS.subscribe(cb)`.

**Правило: любая мутация через API рассылает событие.** Иначе соседняя вкладка
показывает устаревшие данные до ручного обновления страницы.

| Событие | Шлёт | Подписаны |
|---|---|---|
| `employee_created`, `employee_updated` | `employees`, импорт сотрудников | `employees_list` |
| `issue_updated` | `employee_ppe_issues` | `employees_list` (открытая карточка) |
| `norm_updated` | `position_ppe_norms` (создание, правка, удаление, копирование), импорт норм | `norms_list` |
| `item_updated` | `ppe_items` (в т.ч. массовые операции), импорт СИЗ | `ppe_items_list`, `ppe_item_edit_v2` |
| `department_updated` | `departments` | `departments_list`, `department_edit` |
| `position_updated` | `positions` | `positions_list`, `position_edit` |
| `function_updated` | `ppe_functions` | `ppe_functions_list`, `ppe_items_list`, `ppe_item_edit_v2` |
| `size_group_updated` | `ppe_size_groups` | `ppe_size_groups_list`, `ppe_items_list`, `ppe_item_edit_v2`, `employees_list` |
| `size_updated` | `ppe_sizes` (в сообщении есть `size_group_id`) | `ppe_size_groups_list` (модалка своей группы), `employees_list` |
| `unit_updated` | `units` | `units_list`, `ppe_items_list`, `ppe_item_edit_v2` |
| `typical_norm_updated` | `typical_norms` | `typical_norms_list`, `norms_list` (выпадающий список) |
| `user_updated` | `users` | `users_list` |

Особенности:
- массовые операции и импорт шлют `item_id=0` / `employee_id=0` — это «изменилось
  много записей»: списки перечитываются, карточка одной записи — нет;
- рассылка идёт через `app/utils/broadcast.py`: сбой WS логируется, но не
  ломает основной запрос;
- `login`/`logout` события не шлют — это состояние сессии, а не данных.

## Известные ловушки

Каждая из них уже приводила к поломке. Проверять при изменениях
соответствующего кода.

### 1. asyncpg и типы параметров в миграциях

Один параметр, использованный и в `SELECT`, и в сравнении с колонкой,
даёт `inconsistent types deduced` — драйвер не может вывести тип.

```sql
-- плохо: $2 встречается как text и как varchar(50)
INSERT ... SELECT :value ... WHERE size_value = :value

-- хорошо: явное приведение
WHERE size_value = CAST(:value AS varchar(50))
```

**`NULL` в `CAST` тоже ломается.** Для `gender IS NULL` нужна отдельная
ветка SQL без приведения.

### 2. MissingGreenlet

Pydantic при сериализации обходит всю схему и читает **все** поля. Если
`relationship` не загружен через `selectinload`, SQLAlchemy пытается
подгрузить его лениво — в async это невозможно.

**Правило:** набор `selectinload` должен покрывать всю вложенную схему
ответа. Например, `PpeItemRead` включает `function`, `size_group` и
`unit` — все три обязательны в опциях загрузки.

### 3. Порядок в шаблоне: модалка раньше скрипта

Скрипт страницы выполняется в момент подключения. Модалка, объявленная
**после** `<script>`, для него не существует: `getElementById` вернёт
`null`, обработчик упадёт.

Модалки — в блоке `content`, скрипты — в `scripts`.

### 4. Двойной триггер модалки

`data-bs-toggle="modal"` **и** `openCreateModal()` одновременно —
Bootstrap создаёт второй backdrop на каждый клик, экран темнеет слоями.

У кнопок, которые открывает скрипт, не должно быть `data-bs-toggle`.

### 5. Расхождение id между шаблоном и JS

`getElementById('create-form')`, когда форма имеет `id="employee-form"` —
тихий `null` и неработающая кнопка.

### 6. Сроки носки

`app/utils/dates.py`, `add_wear_period` на `relativedelta`. Значения
`wear_period_value` + `wear_period_unit` (`год`, `месяц`, `до износа`).

Для «до износа» срок не считается — `expiry_date` остаётся пустым.

### 7. BOM в сообщении коммита

`Set-Content -Encoding UTF8` в PowerShell 5.1 пишет BOM, а git переносит
его в сообщение как обычный символ: тема коммита начинается с невидимого
`U+FEFF`. Так испорчены `65cef95` и `62938c6` — выглядят нормально,
но первый байт темы не тот, и поиск по префиксу сообщения не находит их.

Текст для `commit -F` писать только без BOM:

```powershell
[System.IO.File]::WriteAllText($tmp, $Message, (New-Object System.Text.UTF8Encoding($false)))
```

Тот же приём обязателен для файла кеша в `push-ppe.ps1`: с BOM первый
символ пути не совпадает, и сохранённый путь перестаёт находиться.

### 9. Одинаковое имя у `const` и `function` в одном IIFE

В `employees_list.js` заголовок модалки возврата — это
`const returnTitle = document.getElementById('return-issue-title')`. Функция
для подсказки кнопки возврата называлась так же — `function returnTitle()`.
`function` поднимается в начало области видимости, поэтому такая пара —
`SyntaxError: Identifier 'returnTitle' has already been declared`: **файл не
выполняется целиком**, страница сотрудников навсегда остаётся в состоянии
«Загрузка…», а в логах API нет ни одного запроса списка.

`node --check` (и любой парсер вроде tree-sitter) показывает это сразу;
«проверка парности скобок» — нет, потому что скобки в порядке. Правило:
новое имя не должно совпадать ни с одним `const`/`let`/`function` того же
файла, даже если объявления далеко друг от друга.

## Схема базы данных

`docs/ppe-tracker-db-schema.pdf` — ER-схема, **основной вид**: лист 20,6 × 10,6″,
по фигуре на таблицу, поля с типами и `PK`/`U`/`NN`, ортогональные связи по
внешним ключам с правилом `ON DELETE`. PDF собирается `reportlab` (шрифты
DejaVu с кириллицей): координаты и маршруты линий задаём сами, поэтому рендер
предсказуем и проверяем — в отличие от `.vsdx`, где Visio интерпретирует
коннекторы по своим правилам.

**Оформление и связи:**
- таблицы раскладываются по колонкам `PDF_COLUMNS` (слева направо: доступ и
  организация → сотрудники и выдачи → нормы → справочники), шапка окрашена по
  смысловой группе (`PDF_GROUPS`, легенда вверху);
- у полей бейджи `PK`/`FK`/`U`, `NN`, у FK — родительская таблица и правило
  `ON DELETE`; строки чередуются «зеброй»;
- линии ортогональные, идут по «шинам» в жёлобах между колонками и не заходят
  на таблицы; цвет линии задаёт родительская таблица, на концах — нотация
  «вилка» (дочерняя) / «черта» (родитель), кружок — FK допускает NULL;
- порядок шин в жёлобе подбирается перебором ради минимума пересечений;
  связь допустима только между соседними колонками (иначе ошибка с
  подсказкой переставить `PDF_COLUMNS`);
- генератор печатает `связей: N · пересечений: M · наложений: 0`; ненулевые
  наложения — ошибка раскладки.

`docs/db-schema.md` — та же схема текстом в mermaid: диффится в git и видна
на GitHub без всяких просмотрщиков.

`docs/ppe-tracker-db-schema.vsdx` — тот же набор таблиц в Visio. Оставлен как
эксперимент: связи Visio рисует по-своему, для проверки схемы используйте PDF.

Генерация всех трёх файлов:

```bash
.venv/bin/python docs/make_er_diagram.py
```

Скрипт читает `information_schema` через `docker compose exec db psql`,
поэтому после новой миграции достаточно запустить его снова. Таблица без
места на листе — это ошибка «добавьте в LAYOUT»: раскладка задана вручную,
иначе связи путаются и схема перестаёт читаться.

`docs/er_template.vsdx` — пустой каркас Visio, взятый из репозитория
библиотеки `vsdx` (MIT). Файл `.vsdx` — это OOXML-пакет, и собирать его с
нуля незачем: генератор подменяет в каркасе только страницу, размер листа и
свойства документа.

**Ловушки, из-за которых схема сначала выглядела сломанной:**

- **В PDF** отступ внутри шапки таблицы задаётся в дюймах: `+ 2.6` вместо
  `+ 0.04` уводило подписи вниз на 2,6 дюйма. Все координаты в генераторе —
  дюймы, включая «мелкие» смещения.
- **В PDF** связи нельзя вести по центру колонки: линия проходит сквозь
  таблицы, стоящие между. Поэтому у колонки есть «шина» сбоку
  (`±0.22″` + разброс), а самоссылка `departments.parent_id` рисуется петлёй.
- **В Visio** `LocPinX`/`LocPinY` нельзя задавать значением `0` при формуле
  `Width*0.5`: Visio берёт значение, а не пересчитывает формулу, и каждая
  фигура съезжает на половину своего размера.
- **В Visio** связи должны быть фигурами на мастере `Dynamic connector`
  (`Master='2'` из каркаса): у собственной 1D-фигуры нет формул коннектора,
  и Visio рисует её как обычный прямоугольник — линия уходит наискось.

### 10. `.dockerignore`: шаблон без `**/` не покрывает вложенные каталоги

`__pycache__` в `.dockerignore` исключает только каталог в корне контекста —
`app/__pycache__` всё равно попадал в образ (проверено: `find /app -name
__pycache__` внутри `ppe-tracker-api:prod`). Для вложенных нужен `**/`:
`**/__pycache__`, `**/*.py[cod]`.

Там же вторая ловушка: `.dockerignore` без `!.env.prod.example` и с широким
`.env.*` скрывает шаблон окружения, а строка `docker` (вместо `dockerfile`)
выкидывает каталог, из которого копируется `docker/entrypoint.sh`, — сборка
падает на `COPY`.

## Прод-запуск

Отдельный образ и compose, dev-запуск (`docker compose up`) не меняется.

```bash
cp .env.prod.example .env.prod      # SECRET_KEY, пароли; файл в .gitignore
docker compose --env-file .env.prod -f docker-compose.prod.yml up -d --build
docker compose --env-file .env.prod -f docker-compose.prod.yml exec api python create_admin.py
```

**`--env-file .env.prod` обязателен, это не украшение.** `env_file: .env.prod`
у `api` кладёт переменные только **внутрь** контейнера api; `${...}` в самом
yml compose подставляет из `.env` или из `--env-file`. Без флага у `db`
остаются пустые `POSTGRES_USER`/`PASSWORD`/`DB`, Postgres не создаёт
пользователя, `db` уходит в `unhealthy`, а `api` не стартует из-за
`depends_on: service_healthy` — при этом в выводе только три строчки
`variable is not set`. Теперь эти переменные помечены `${POSTGRES_USER:?...}`,
и compose останавливается с внятным текстом.

Для пустой базы — `AUTO_MIGRATE=1`: миграции применятся на старте
(`миграции применены (попытка 1)` в логах api). Для проверки по http —
`SESSION_COOKIE_SECURE=false`, иначе браузер не пришлёт cookie и вход молча
не сработает.

Проверено на реальном запуске 6 ноября 2026: `up -d --build` с нуля,
все 29 миграций на старте, `api` и `db` — `healthy`, `/healthz` → 200,
`/login` → 200, `/docs` → 404 (значит `ENVIRONMENT=production` применился).

### Образ с данными из dev-базы (`make-data-image.sh`)

Отдельная задача: «собрать образ, в котором уже есть данные». Собирается
скриптом из корня клона:

```bash
chmod +x make-data-image.sh && ./make-data-image.sh
# → ppe-tracker-api:prod, затем ppe-tracker-api:data
```

Что делает: поднимает dev-базу (`docker compose up -d db`), снимает `pg_dump`,
собирает прод-образ и поверх — слой с дампом (`dockerfile.data`). При первом
старте на **пустой** базе `docker/entrypoint-data.sh` применяет миграции,
заливает дамп и только потом запускает uvicorn.

**Почему дамп, а не копия `PGDATA` внутрь образа.** Каталог данных Postgres
привязан к мажорной версии сервера, к control-файлу с system identifier и к
правам каталога. Копия «как есть» работает только на той же версии Postgres и
ломается при смене uid. Дамп переносится куда угодно и разворачивается на
схеме, собранной штатными миграциями.

**Порядок в `entrypoint-data.sh` важен:**

1. ждать, пока база ответит (через `app.db.session`, чтобы не дублировать
   настройки подключения);
2. `alembic upgrade head` — схема должна быть до `psql`;
3. маркер `/app/data/.dump-loaded` — дамп применяется **один раз**, повторный
   старт контейнера не накатывает данные поверх пользовательских правок;
4. проверка «база пустая» (`SELECT count(*) FROM users`): в непустую базу
   дамп заливается только с `FORCE=1`, иначе контейнер на чужом томе молча
   сотрёт данные;
5. `psql --single-transaction --set ON_ERROR_STOP=1` — ошибка в дампе не
   оставит базу наполовину заполненной.

**`alembic_version` из дампа вырезан.** Данные этой таблицы исключены через
`--exclude-table-data`, а её DDL убран `grep`-ом: `pg_dump --clean` иначе
создаёт таблицу заново, и на свежемигрированной базе получается
`relation "alembic_version" already exists`. Версия — дело alembic, а не дампа.

**`--build-arg BASE_IMAGE`** в `dockerfile.data` — так образ с данными
наследует уже собранный прод-образ, пересборка зависимостей не нужна.

**Дамп — персональные данные.** Скрипт удаляет временный контекст после
сборки (кроме `-k`); `.dockerignore` запрещает `data/` и `**/dump.sql` в
обычном контексте. Готовый образ тоже содержит эти данные: в общий registry
его публиковать нельзя.

Требование к базовому образу: `psql` из `postgresql-client`, uvicorn из
`python:3.11-slim`-образа. Скрипт — POSIX `sh`, должен работать и из WSL, и
на dev-машине там, где есть docker compose.

Отличия от dev:

| | dev (`docker-compose.yml`) | prod (`docker-compose.prod.yml`) |
|---|---|---|
| образ | `dockerfile`, `COPY . .` | `dockerfile.prod`: multi-stage, только нужные файлы |
| пользователь | root | `app` (uid 10001) |
| код | bind-mount `./app:/app/app` | только из образа |
| запуск | `uvicorn --reload` | `uvicorn --proxy-headers`, без reload, `CMD` в образе |
| порт api | `8000:8000` наружу | `127.0.0.1:8000` — закрывает reverse-proxy |
| порт БД | `5433:5432` наружу | не публикуется |
| том БД | `postgres_data` | `ppe_prod_pgdata` (данные не смешиваются) |
| `/docs`, `/redoc`, `/openapi.json` | открыты | 404 при `ENVIRONMENT=production` |
| 500 | текст исключения | «Внутренняя ошибка сервера», детали в логе |
| healthcheck | нет | `api` → `/healthz` (проверяет БД), `db` → `pg_isready` |
| секреты | `.env` рядом, попадал в образ | `.env.prod` монтируется как env, в образ не попадает |

**`.dockerignore` обязателен**: без него `COPY . .` затягивал `.env` (ключ и
пароль БД в слое образа), `.venv` на Python 3.14 (237 МБ), `.git` (13 МБ) и
`__pycache__`. После появления файла образ: 571 МБ вместо 885 МБ, из них кода
912 КБ. Если образ с секретами успел куда-то уехать — ротировать `SECRET_KEY`
и пароль БД.

**Ограничения, которые нужно помнить:**

- **Миграции с нуля теперь собираются** (было ловушкой 8, исправлено —

  проходит все 29 ревизий; проверено на `postgres:16-alpine` и на

- `SESSION_COOKIE_SECURE=true` работает только вместе с HTTPS на прокси.

- `create_admin.py` входит в образ: без него прод-базу не наполнить. Запускать

### 11. CRLF в `entrypoint.sh`: «no such file or directory», хотя файл на месте

Сборка из **Windows-клона** дала образ, который падал на любом запуске:

```
exec /usr/local/bin/entrypoint.sh: no such file or directory
```

Файл при этом лежит в образе — ядро ищет интерпретатор из шебанга и читает его
как `/bin/sh\r`. Причина: в репозитории файл хранится с LF (`i/lf`), но на
Windows включён глобальный `core.autocrlf=true` (`C:/Program Files/Git/etc/
gitconfig`), поэтому рабочая копия чекаутится с CRLF, а **контекст сборки —
это рабочая копия**. На WSL-клоне (LF) ошибка не воспроизводится: образ там
собирался и проверялся.

Проверить, не приехало ли CRLF в образ, можно без Docker:

```powershell
$b = [IO.File]::ReadAllBytes('docker/entrypoint.sh'); $b[0..9] -join ' '
# правильно: 23 21 2F 62 69 6E 2F 73 68 0A  (…/sh + LF)
```

Лечение двойное, оба нужны:

1. **`.gitattributes`** — `* text=auto eol=lf` фиксирует LF на всех машинах
   независимо от `core.autocrlf`. Бинарные расширения помечены `binary`.
   Рабочие копии уже существующих файлов `.gitattributes` сам не
   перенормализует: после правки — `git add --renormalize .` (или один раз
   переписать файл с LF).
2. **`sed -i 's/\r$//'` в `dockerfile.prod`** перед `chmod` — страховка на
   случай контекста, собранного в обход git (архив, копия папки).

Само по себе `dockerfile.prod` с CRLF собирается нормально: Docker построчно
читает директивы и переносы гасит. Ломаются только файлы, которые исполняет
ядро Linux: `.sh`, а также любые shebang-скрипты.

### 12. Автогенерация выдаёт `drop_table` вместо `add_column`

Корень обрыва из ловушки 8. Когда Alembic при `--autogenerate` не видит
таблицу в базе, он считает её лишней и вместо правки колонки пишет
`op.drop_table(...)`. Это случилось дважды:

- `e1e06dfc6360` («add unique constraint to position_ppe_norms») —
  `drop_table('position_ppe_norms')`, хотя таблицу создал `bd09b9140447`
  предыдущим шагом;
- `42b7bb81cc04` («add gender to ppe_sizes») — `drop_table('ppe_sizes')`
  вместо `add_column(gender)`, хотя таблицу создал `5b495550fcfc`.

Последствия каскадом: следующие ревизии обращаются к удалённой таблице и
падают. Так «одна миграция с `drop`» утащила за собой `a95a41654eeb`,
`9dbb6662bf81`, `f3bb1b7dee7d` и `cc31f1fe06fd`.

**Правило: миграцию проверяют на ПУСТОЙ базе, а не на рабочей.** На рабочей
всё зелено, потому что таблица уже есть, и `drop_table` проходит там лишь
потому, что миграции когда-то применялись по одной, а таблица появлялась
позже. Признак в файле — `op.drop_table(...)` или `op.drop_constraint(...)`
в `upgrade()` ревизии, название которой обещает *добавление*. Такое
`drop_table` почти наверняка ошибка автогенерации.

Там же вторые грабли: **`op.f('имя')` подставляет naming convention**, а не
буквальное имя. Если ограничение создано «сырым» SQL, до появления convention
или в базе его имя отличается — `drop_constraint(op.f('...'))` ищет не то
имя и падает. Надёжнее `ALTER TABLE ... DROP CONSTRAINT IF EXISTS`.

## Рабочая среда: home, work и docker

Машин две, а сред, в которых идёт работа, — три. В переписке и документах
они называются так:

| Имя | Путь | Роль |
|---|---|---|
| **home** | `C:\projects\ppe-tracker` | правки кода, git, commit, push |
| **work** | `C:\projects\ppe-tracker` (Windows-клон) | то же: правки кода, git, commit, push |
| **docker** | VS Code на work внутри WSL, `/home/vagur/projects/ppe-tracker` | запуск и проверка: `docker compose`, `alembic`, `.env`, БД, браузер |

**`docker` — не третья машина, а среда запуска.** Это VS Code на work,
подключённый к WSL (`ppe-tracker [WSL: Ubuntu]`): там лежит WSL-клон, и в
том же WSL-дистрибутиве Docker Desktop поднимает движок с контейнерами
`api` и `db`. Отдельное имя понадобилось потому, что «work» — это
Windows-клон, где приложение не запущено, а «docker» — тот клон, на коде
которого приложение действительно работает. Приглашение `(ppe-tracker)`
в терминале этой среды — активированный `.venv` из клона.

**Работаем мы в этой среде.** Сессии ассистента, правки и проверки идут
здесь — в VS Code на work, подключённом к WSL, — а не в Windows-клоне.
Windows-клон остаётся для правок «руками» и для `push-ppe.cmd`.

Признаки, по которым видно, что сессия именно здесь (проверено 5 ноября
2026):

| Признак | Значение в среде docker |
|---|---|
| `hostname` | `MPC-W11-WRK` — та же машина, что work |
| `uname -r` | `6.18.54.1-microsoft-standard-WSL2` |
| `WSL_DISTRO_NAME` | `Ubuntu` |
| `TERM_PROGRAM` | `vscode` |
| `/.dockerenv` | **отсутствует** — шелл не в контейнере |
| `wslpath -w .` | `\\wsl.localhost\Ubuntu\home\vagur\projects\ppe-tracker` |
| `docker info` | `docker-desktop`, ядро WSL2, драйвер `overlayfs` |

**Ловушка: «среда docker» ≠ «внутри контейнера».** Шелл живёт в WSL, а
контейнеры `api` и `db` — рядом, в том же WSL-дистрибутиве. Поэтому
`pip install` в шелле не меняет образ, `.venv` не виден приложению, а
`python -c "import ..."` проверяет venv, а не то, что запущено в api.
Код приложения проверяется только через `docker compose exec api ...`.

**Клон лежит по одному и тому же пути на обеих машинах**, поэтому все
пути в этом документе к машине не привязаны. Правки можно делать на
любой — они сходятся через GitHub: `push` на одной, `git pull` на другой.
Раньше здесь было «home — код, work — только запуск»; на деле правки
уходят и с work, а основная работа идёт в docker.

**Где что выполняется:**

- **home** — только код и git. Ни `docker compose`, ни `alembic`: на этой
  машине нет ни Docker, ни `.env`, ни базы. Сюда `.env` и не нужен — он
  в `.gitignore` и живёт только в WSL-клоне.
- **work** — Windows-клон: код и git, как на home. Docker и `.env` на
  машине есть, но к этой копии не относятся — они принадлежат среде
  **docker**.
- **docker** — и код, и всё, что связано с запуском: `docker compose up`,
  `alembic upgrade head`, проверка в браузере. Docker берётся из
  Docker Desktop в WSL, работа идёт вручную через VS Code. Правки в `app/`
  видны приложению сразу: каталог смонтирован в контейнер, uvicorn с
  `--reload`.

### Две копии проекта на work

На work проект существует дважды, и это не одно и то же:

| Копия | Где | Что в ней |
|---|---|---|
| Windows-клон (среда **work**) | `C:\projects\ppe-tracker` | рабочее дерево для правок и git; `.env`, `.venv`, `.vscode` отсутствуют |
| WSL-клон (среда **docker**) | `/home/vagur/projects/ppe-tracker`, открыт в VS Code как `ppe-tracker [WSL: Ubuntu]` | `.env`, `.venv`, `.vscode`, `.ruff_cache`; отсюда запускают `docker compose` |

В приглашении WSL-терминала видно `(ppe-tracker)` — это активированное
окружение `.venv` из клона, а не отдельная копия проекта. Раз работа идёт
в этой копии, в переписке она и называется средой **docker**.

Копии независимы: у каждой свой `.git` и свои неотслеживаемые файлы.
Сходятся они только через GitHub. Отсюда ловушка: **правка в
Windows-клоне не видна приложению, пока не сделан `git pull` в
WSL-клоне** — приложение работает на том коде, который лежит рядом с
`docker-compose.yml`, а не на том, который правили.

Из Windows-сессии (среды **home** и **work**) ассистент до WSL не
достаёт: `\\wsl.localhost\Ubuntu` отвечает «Отказано в доступе». Поэтому
`git pull`, `docker compose` и `alembic` в WSL-клоне выполняет человек
через VS Code — либо ассистент из среды **docker**, где эти команды
доступны напрямую.

**Цикл работы:**

1. Правки на той машине, где удобно, затем из `C:\projects` —
   `push-ppe.cmd` (двойной клик или `.\push-ppe.cmd -Message "..."`).
   Не `push-ppe.ps1` — почему, см. ниже.
2. На второй машине: `git pull`, а в среде **docker** при необходимости
   `docker compose restart api` и `alembic upgrade head`.
3. В среде **docker** — ещё один `git pull` **в WSL-клоне**, иначе браузер
   покажет старую версию.

### Скрипт push живёт вне репозитория

`push-ppe.ps1` и `push-ppe.cmd` лежат **в `C:\projects`, на уровень выше
папки проекта**, и в репозиторий не входят. Так сделано намеренно: скрипт
сам находит клон рядом с собой (`<папка скрипта>\ppe-tracker`), поэтому
после перезагрузки путь вспоминать не нужно.

- **Запускать обёртку `push-ppe.cmd`, а не `.ps1`.** Файл `.ps1` в системе
  открывается в редакторе (ассоциация `UserChoice` ведёт в текстовый
  редактор), а политика выполнения в Windows — `Restricted`: все области
  `Undefined`, то есть сценарии запрещены. Двойной клик по `.ps1` поэтому
  только открывает текст, а не запускает его. Обёртка вызывает
  `powershell -NoProfile -ExecutionPolicy Bypass -File ...`, и работает
  при любых настройках политики.
- Из `C:\projects`: `.\push-ppe.cmd -Status`, `.\push-ppe.cmd -Message "..."`.
  Из корня репозитория путь не найдётся — там скрипта нет.
- При двойном клике окно закрывается сразу после успеха (пауза в обёртке
  стоит только на ошибку). Нужен вывод на экран — запускать из терминала.
- Скрипт вызывает `git` без полного пути, ему нужен
  `C:\Program Files\Git\cmd` в `PATH` (в машинном `PATH` он есть).
- Сообщение коммита скрипт передаёт через временный файл и
  `-c i18n.commitEncoding=UTF-8`: многострочный текст с кириллицей
  ломается в аргументе командной строки.
- **На каждой машине своя копия скрипта**, и git их не синхронизирует:
  скрипт лежит вне репозитория. Правка, сделанная на одной машине, на
  другой не появится — повторять вручную. Так и вышло с BOM: на work
  исправлено, на home копия осталась с прежним `Set-Content`.

### Если git запускает ассистент

Ограниченная среда, в которой ассистент выполняет команды, может мешать
сильнее обычной консоли. Проверено на work 4 ноября 2026:

- `git` может отсутствовать в `PATH` процесса → вызывать по полному пути
  `C:\Program Files\Git\cmd\git.exe`.
- Штатный TLS-бэкенд `schannel` падает с `SEC_E_NO_CREDENTIALS` →
  `git -c http.sslBackend=openssl ...`.
- Сохранённые креды недоступны: помощник не запускается
  (`sh.exe: couldn't create signal pipe`), поэтому push требует разового
  расширения прав на команду. Анонимный `ls-remote` к публичному
  репозиторию работает и без этого.
- Токен с правом `repo` сохраняется через окно входа GCM как запись
  `git:https://github.com`; повторно вводить его не нужно. Проверено:
  push в GitHub проходит.

**Репозиторий вне OneDrive — намеренно.** Раньше он лежал в синхронизируемой
папке, и `.git` мог попасть в момент записи: это даёт битые объекты и
конфликтные копии вроде `index (1).lock`. Резервная копия и синхронизация —
на GitHub, OneDrive для этого не нужен.
