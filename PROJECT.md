# PPE Tracker — контекст проекта

Документ для продолжения работы на любой машине и с любым ассистентом.
Описывает архитектуру, принятые решения и известные ловушки — то, чего не
видно в коде с первого взгляда.

---

## Правило обновления — читать до начала работы

**Этот файл ведётся вместе с кодом, а не «потом».** Изменение, которое
затрагивает архитектуру, схему данных или открывает новую ловушку, должно
дополнять PROJECT.md **в том же коммите**. Иначе контекст теряется, и
следующий человек (или ассистент) наступит на ту же грабли.

Критерий, что писать:

| Писать | Не писать |
|---|---|
| Новое архитектурное решение и его причина | «добавил кнопку», «поправил стиль» |
| Ловушка, которая уже ломала проект, и как её распознать | описание текущей задачи |
| Изменение схемы данных, новая миграция | детали, которые видны в коде |
| Правило, которое легко нарушить незаметно | то, что устареет через месяц |

Проверка перед коммитом: если изменение удивит того, кто откроет проект
через полгода — оно должно быть здесь.

## Что это

Учёт средств индивидуальной защиты (СИЗ) на предприятии: справочники,
сотрудники, нормы выдачи, фактические выдачи со сроками носки.

**Стек:** FastAPI + SQLAlchemy 2.0 (async, asyncpg) + PostgreSQL + Alembic.
Фронтенд — Jinja2-шаблоны, Bootstrap 5.3 с CDN, обычный JS без сборщика.

**Запуск:** Docker Compose (api + db), код монтируется в контейнер,
uvicorn с `--reload`.

## Предметная область

```
Department (дерево) → Position → PositionPpeNorm → PpeItem
Employee → EmployeePpeSize (размеры по группам)
Employee → EmployeePpeIssue (выдачи)
PpeItem → PpeFunction, PpeSizeGroup, Unit
PpeSizeGroup → PpeSize (значения размеров)
```

- **Норма** — сколько и на какой срок положено должности.
- **Выдача** — что фактически выдано сотруднику, со сроком годности,
  рассчитанным из нормы.
- **Размер сотрудника** — по одной записи на размерную группу
  (`uq_employee_size_group`).

## Ключевые решения

### Авторизация и CSRF

- Сессия через `SessionMiddleware`, cookie `ppe_session`.
- `SECRET_KEY` обязателен, приложение падает на старте без него — сделано
  осознанно вместо тихого дефолта.
- CSRF — double-submit: токен в сессии и в `<meta name="csrf-token">`,
  клиент шлёт его в `X-CSRF-Token` для POST/PUT/PATCH/DELETE.
- **Порядок зависимостей важен:** `require_csrf` подключён раньше
  `get_current_active_user`, чтобы отклонённый запрос не открывал
  соединение с БД. Следствие: неавторизованный небезопасный запрос
  возвращает 403, а не 401.

### Пагинация

`GET /api/v1/<список>/` принимает `page`, `page_size`, `search` и флаг
`paginated`.

**Флаг обязателен:** без `paginated=true` эндпоинт отдаёт **обычный
массив**. Это нужно выпадающим спискам, которым требуются все значения
сразу (выбор подразделения, должности, СИЗ).

С `paginated=true` — конверт `{items, total, page, page_size, pages}`.

Сортировка всегда явная. Без `ORDER BY` Postgres вправе менять порядок
между запросами, и при `LIMIT/OFFSET` это даёт дубли и пропуски на
границах страниц.

### Несколько норм на пару «должность + СИЗ»

Ограничение `uq_position_ppe_item` **снято** миграцией `a9f3c06b2d18`.
Причина: в матрице норм Минтруда у одной пары есть основное наименование
и до четырёх альтернатив.

При выдаче берётся **первая по id** норма пары. В коде поэтому стоит
`scalars().first()`, а не `scalar_one_or_none()` — последний при дублях
бросает `MultipleResultsFound` и даёт 500.

**В модели ограничения тоже нет** — в `PositionPpeNorm.__table_args__`
остался только `Index("ix_position_ppe_norms_position_item")`. Если вернуть
`UniqueConstraint`, `alembic revision --autogenerate` попытается
восстановить ограничение и упадёт на базе, где альтернативы уже есть.

Следствие: **нигде не сравниваем нормы по одной паре.** Копирование норм
(`POST /position_ppe_norms/copy`) считает дублем только полное совпадение
(СИЗ + срок носки + количество) и копирует альтернативы. Импорт норм
обновляет первую по id норму пары, а не падает с `MultipleResultsFound`.

### Выдача СИЗ: размер списком, количество из нормы

Модалка выдачи (`#issueModal` в `templates/employees/list.html`, логика в
`static/js/employees_list.js`) заполняется сама — иначе выдача
превращалась в переписывание справочников руками:

- **Наименование** — только СИЗ из норм должности сотрудника. Список всех
  СИЗ позволял выдать что угодно мимо нормы.
- **Размер** — `select` из справочника размеров той размерной группы,
  которая задана у СИЗ (`/api/v1/ppe_sizes/?size_group_id=...`), с фильтром
  по полу сотрудника (размер без пола подходит обоим). Предвыбран размер
  из карточки — вкладка «Размеры СИЗ». Раньше это было поле ввода: значения
  вроде «58 размер» не совпадали ни с карточкой, ни со справочником.
- **Количество** — подставляется из нормы выдачи должности.

Размер из карточки, которого нет в справочнике, остаётся в списке отдельным
вариантом с пометкой «из карточки»: иначе подстановка молча терялась и
вместо своего размера сотрудник получал чужой из начала списка.

При расхождении размера с карточкой или количества с нормой показывается
предупреждение (`#issue-warning`), **но выдача не блокируется**:
обоснованное отклонение от нормы бывает нужным, а молчаливая запись
«чего-нибудь» — ошибка учёта.

**Количество сравниваем по первому числу**, а не строкой: в нормах
встречается «1 пара» и «2 комплекта», а в выдаче — «1». Строгое равенство
давало ложные предупреждения на каждом шаге. Если чисел нет вовсе,
сравниваем строки целиком (`firstNumber` в `employees_list.js`).

Срок носки по-прежнему считает сервер: клиент только подставляет поля.

### Вкладки — обычные страницы, не iframe

Раньше вкладки были iframe: модалки открывались внутри рамки (backdrop
накрывал только таблицу), прокрутка была двойной. Теперь у каждой вкладки
свой URL: `/ppe-items`, `/norms`, `/ppe-functions`, `/ppe-size-groups`,
`/units`, `/departments`, `/positions`.

`/ppe` и `/structure` — редиректы на первые вкладки.

### Модалки вместо страниц редактирования

Справочники и сотрудник редактируются в модалках. Страница
`/employees/{id}/edit` — редирект на список.

У модалки создания и редактирования один и тот же DOM: переключаются
заголовок, текст кнопки и скрытое поле `version`.

### Дизайн-система

Всё в `app/static/css/app.css`. Токены: `--brand` (#5b2c8a, фиолетовый —
действия и заголовки), `--accent` (#ff6600, оранжевый — удаление и отмена),
радиусы, тени, отступы `--space-*`.

**Правила:** никаких inline-стилей, никаких `!important`.
Иконки: `.btn-icon` фиолетовая, `.btn-icon--danger` оранжевая.
Бейджи: только `badge-purple` и `badge-orange`.

Списки: `.data-table--dense` (отступ ячейки 6px), 20 строк на страницу.

## Известные ловушки

Каждая из них уже приводила к поломке. Проверять при изменениях
соответствующего кода.

### 1. asyncpg и типы параметров в миграциях

Один параметр, использованный и в `SELECT`, и в сравнении с колонкой,
даёт `inconsistent types deduced` — драйвер не может вывести тип.

```sql
-- плохо: $2 встречается как text и как varchar(50)
INSERT ... SELECT :value ... WHERE size_value = :value

-- хорошо: явное приведение
WHERE size_value = CAST(:value AS varchar(50))
```

**`NULL` в `CAST` тоже ломается.** Для `gender IS NULL` нужна отдельная
ветка SQL без приведения.

### 2. MissingGreenlet

Pydantic при сериализации обходит всю схему и читает **все** поля. Если
`relationship` не загружен через `selectinload`, SQLAlchemy пытается
подгрузить его лениво — в async это невозможно.

**Правило:** набор `selectinload` должен покрывать всю вложенную схему
ответа. Например, `PpeItemRead` включает `function`, `size_group` и
`unit` — все три обязательны в опциях загрузки.

### 3. Порядок в шаблоне: модалка раньше скрипта

Скрипт страницы выполняется в момент подключения. Модалка, объявленная
**после** `<script>`, для него не существует: `getElementById` вернёт
`null`, обработчик упадёт.

Модалки — в блоке `content`, скрипты — в `scripts`.

### 4. Двойной триггер модалки

`data-bs-toggle="modal"` **и** `openCreateModal()` одновременно —
Bootstrap создаёт второй backdrop на каждый клик, экран темнеет слоями.

У кнопок, которые открывает скрипт, не должно быть `data-bs-toggle`.

### 5. Расхождение id между шаблоном и JS

`getElementById('create-form')`, когда форма имеет `id="employee-form"` —
тихий `null` и неработающая кнопка.

### 6. Сроки носки

`app/utils/dates.py`, `add_wear_period` на `relativedelta`. Значения
`wear_period_value` + `wear_period_unit` (`год`, `месяц`, `до износа`).

Для «до износа» срок не считается — `expiry_date` остаётся пустым.

### 7. BOM в сообщении коммита

`Set-Content -Encoding UTF8` в PowerShell 5.1 пишет BOM, а git переносит
его в сообщение как обычный символ: тема коммита начинается с невидимого
`U+FEFF`. Так испорчены `65cef95` и `62938c6` — выглядят нормально,
но первый байт темы не тот, и поиск по префиксу сообщения не находит их.

Текст для `commit -F` писать только без BOM:

```powershell
[System.IO.File]::WriteAllText($tmp, $Message, (New-Object System.Text.UTF8Encoding($false)))
```

Тот же приём обязателен для файла кеша в `push-ppe.ps1`: с BOM первый
символ пути не совпадает, и сохранённый путь перестаёт находиться.

### 8. Цепочка миграций не собирается с нуля

`alembic upgrade head` на пустой базе не пройдёт: миграция
`e1e06dfc6360` («add unique constraint to position_ppe_norms») в
`upgrade()` делает `DROP TABLE position_ppe_norms` и не создаёт таблицу
заново, а следующая `a95a41654eeb` обращается к её колонкам (`ALTER`,
`DROP INDEX`). Таблица появляется только в `bd09b9140447`, то есть до
удаления.

Распознать, не поднимая базу:

```bash
alembic upgrade head --sql | grep -E '(CREATE|DROP) TABLE position_ppe_norms'
```

В выводе будет `DROP TABLE` без обратного `CREATE`. Отдельно: `--sql`
обрывается на первой data-миграции (`b7e1c93d5a24` обращается к соединению),
это нормально — нужные строки идут раньше. Рабочую базу на work это не
затрагивает, она уже на голове, но чистый разворот по README сейчас не
проходит. Пока не исправлено.

## Проверки перед коммитом

```powershell
ruff check .                     # должен быть All checks passed!
node --check app/static/js/employees_list.js   # и остальные JS
alembic heads                    # одна голова, цепочка цельная
```

**Где что лежит** (проверено 4 ноября 2026):

- `node` v26 — в PATH на Windows, `node --check` работает сразу, ставить
  нечего. **В среде docker (WSL) node нет**: проверять синтаксис JS можно
  только Windows-нодой (`/mnt/c/Program Files/nodejs/node.exe`), и она не
  читает файлы по UNC-пути WSL — падает с
  `Cannot read package config \\?\UNC\wsl.localhost\package.json`. Поэтому
  файл копируют в Windows-каталог (например, `C:\Users\Public\ppe-js-check`)
  и проверяют там.
- `ruff` 0.17.3 — в среде **docker** из `(ppe-tracker)` venv, а на Windows
  в `%LOCALAPPDATA%\dsh-tools\ruff.exe` (standalone-бинарник, Python не
  нужен). Версии совпадают намеренно: набор правил у ruff растёт от
  версии к версии, и разница версий даёт разный результат на одном коде.
- Кэш ruff — `.ruff_cache/`. В `.gitignore` его добавлять не нужно:
  ruff кладёт внутрь свой `.gitignore` со звёздочкой, поэтому `git add -A`
  в `push-ppe.ps1` его не подхватит.

**`.venv` в среде docker — только для линтера и IDE, приложение в нём не
запускается.** Зависимости для запуска стоят в образе (`dockerfile` +
`requirements.txt`), поэтому неполный venv контейнеру не мешает, но мешает
проверкам: без `uv pip install -r requirements.txt` падает
`from app.main import app` на `No module named 'jinja2'`. По той же причине
версии в `requirements.txt` запинены: незапиненные пакеты
(`jinja2`, `python-multipart`, `pandas`, `openpyxl`, `python-dateutil`,
`itsdangerous`) давали в venv не те версии, что в работающем образе, и
локальная проверка расходилась с контейнером.

**`ruff format` в проекте не применяется.** `ruff format --check .` говорит
«45 files would be reformatted» — код никогда не прогонялся через
форматтер, и разовый `ruff format` дал бы дифф на 45 файлов, не связанный
с задачей. Длину строк и пробелы держит `ruff check`, форматирование —
отдельное решение, а не побочный эффект проверки.

И проверить PROJECT.md: если изменение затрагивает архитектуру, схему
данных или открыло новую ловушку — файл должен быть дополнен в этом же
коммите (см. «Правило обновления» в начале).

Тесты лежат **вне репозитория**, в каталоге `.tmp/` рядом с папкой проекта
(на машине разработки — `default-workspace/.tmp`): `verify_auth.py`,
`render_pages.py`, `test_csrf.py`, `test_pagination.py`, `test_ids.py`,
`test_modals.py`, `test_modal_order.py`, `check_ui.py`,
`check_migrations.py` и другие. Запускаются при `PYTHONPATH`, включающем
виртуальное окружение с зависимостями.

**`render_pages.py`** рендерит все страницы через TestClient и ловит
ошибки шаблонов.
**`test_ids.py`** сверяет `getElementById(...)` в JS с `id` в разметке.
**`test_modal_order.py`** ищет модалки внутри блока `scripts`.

## Git

Remote: `https://github.com/Death-Router/ppe-tracker` (ветка `main`).

**Push с машины разработки требует токена** — SSH не проходит через
локальный прокси/VPN. Personal access token с галочкой `repo`.

Токен сохраняется **на каждой машине отдельно** — Windows Credential
Manager не переносится, запись `git:https://github.com` (пользователь
`Death-Router`) появляется после первого входа через окно GCM. На work
это уже сделано и проверено 4 ноября 2026 реальной записью в GitHub,
а не только сухим прогоном.

Скрипт push и токен — независимые вещи: `push-ppe.ps1` лежит рядом
с проектом, а не в нём, поэтому правки в скрипте **не разъезжаются
через git**. На второй машине его нужно править отдельно.

Сообщения коммитов — по-русски, через файл:
`git -c i18n.commitEncoding=UTF-8 commit -F message.txt`.

Формат: тип(область), затем зачем изменение, а не только что именно.
Причины важнее деталей — они восстанавливают контекст.

они называются так:

| Имя | Путь | Роль |
|---|---|---|
| **home** | `C:\projects\ppe-tracker` | правки кода, git, commit, push |
| **work** | `C:\projects\ppe-tracker` (Windows-клон) | то же: правки кода, git, commit, push |
| **docker** | VS Code на work внутри WSL, `/home/vagur/projects/ppe-tracker` | запуск и проверка: `docker compose`, `alembic`, `.env`, БД, браузер |

**`docker` — не третья машина, а среда запуска.** Это VS Code на work,
подключённый к WSL (`ppe-tracker [WSL: Ubuntu]`): там лежит WSL-клон, и в
том же WSL-дистрибутиве Docker Desktop поднимает движок с контейнерами
`api` и `db`. Отдельное имя понадобилось потому, что «work» — это
Windows-клон, где приложение не запущено, а «docker» — тот клон, на коде
которого приложение действительно работает. Приглашение `(ppe-tracker)`
в терминале этой среды — активированный `.venv` из клона.

**Работаем мы в этой среде.** Сессии ассистента, правки и проверки идут

| `WSL_DISTRO_NAME` | `Ubuntu` |
| `TERM_PROGRAM` | `vscode` |
| `/.dockerenv` | **отсутствует** — шелл не в контейнере |
| `wslpath -w .` | `\\wsl.localhost\Ubuntu\home\vagur\projects\ppe-tracker` |
| `docker info` | `docker-desktop`, ядро WSL2, драйвер `overlayfs` |

**Ловушка: «среда docker» ≠ «внутри контейнера».** Шелл живёт в WSL, а
контейнеры `api` и `db` — рядом, в том же WSL-дистрибутиве. Поэтому
`pip install` в шелле не меняет образ, `.venv` не виден приложению, а
`python -c "import ..."` проверяет venv, а не то, что запущено в api.
Код приложения проверяется только через `docker compose exec api ...`.

**Клон лежит по одному и тому же пути на обеих машинах**, поэтому все
пути в этом документе к машине не привязаны. Правки можно делать на
любой — они сходятся через GitHub: `push` на одной, `git pull` на другой.
Раньше здесь было «home — код, work — только запуск»; на деле правки
уходят и с work, а основная работа идёт в docker.

**Где что выполняется:**

- **home** — только код и git. Ни `docker compose`, ни `alembic`: на этой
  машине нет ни Docker, ни `.env`, ни базы. Сюда `.env` и не нужен — он
  в `.gitignore` и живёт только в WSL-клоне.
- **work** — Windows-клон: код и git, как на home. Docker и `.env` на
  машине есть, но к этой копии не относятся — они принадлежат среде
  **docker**.
- **docker** — и код, и всё, что связано с запуском: `docker compose up`,
  `alembic upgrade head`, проверка в браузере. Docker берётся из
  Docker Desktop в WSL, работа идёт вручную через VS Code. Правки в `app/`
  видны приложению сразу: каталог смонтирован в контейнер, uvicorn с
  `--reload`.

### Две копии проекта на work

На work проект существует дважды, и это не одно и то же:

| Копия | Где | Что в ней |
|---|---|---|
| Windows-клон (среда **work**) | `C:\projects\ppe-tracker` | рабочее дерево для правок и git; `.env`, `.venv`, `.vscode` отсутствуют |
| WSL-клон (среда **docker**) | `/home/vagur/projects/ppe-tracker`, открыт в VS Code как `ppe-tracker [WSL: Ubuntu]` | `.env`, `.venv`, `.vscode`, `.ruff_cache`; отсюда запускают `docker compose` |

В приглашении WSL-терминала видно `(ppe-tracker)` — это активированное
окружение `.venv` из клона, а не отдельная копия проекта. Раз работа идёт
в этой копии, в переписке она и называется средой **docker**.

Копии независимы: у каждой свой `.git` и свои неотслеживаемые файлы.
Сходятся они только через GitHub. Отсюда ловушка: **правка в
Windows-клоне не видна приложению, пока не сделан `git pull` в
WSL-клоне** — приложение работает на том коде, который лежит рядом с
`docker-compose.yml`, а не на том, который правили.

Из Windows-сессии (среды **home** и **work**) ассистент до WSL не
достаёт: `\\wsl.localhost\Ubuntu` отвечает «Отказано в доступе». Поэтому
`git pull`, `docker compose` и `alembic` в WSL-клоне выполняет человек
через VS Code — либо ассистент из среды **docker**, где эти команды
доступны напрямую.

**Цикл работы:**

1. Правки на той машине, где удобно, затем из `C:\projects` —
   `push-ppe.cmd` (двойной клик или `.\push-ppe.cmd -Message "..."`).
   Не `push-ppe.ps1` — почему, см. ниже.
2. На второй машине: `git pull`, а в среде **docker** при необходимости
   `docker compose restart api` и `alembic upgrade head`.
3. В среде **docker** — ещё один `git pull` **в WSL-клоне**, иначе браузер
   покажет старую версию.

### Скрипт push живёт вне репозитория

`push-ppe.ps1` и `push-ppe.cmd` лежат **в `C:\projects`, на уровень выше
папки проекта**, и в репозиторий не входят. Так сделано намеренно: скрипт
сам находит клон рядом с собой (`<папка скрипта>\ppe-tracker`), поэтому
после перезагрузки путь вспоминать не нужно.

- **Запускать обёртку `push-ppe.cmd`, а не `.ps1`.** Файл `.ps1` в системе
  открывается в редакторе (ассоциация `UserChoice` ведёт в текстовый
  редактор), а политика выполнения в Windows — `Restricted`: все области
  `Undefined`, то есть сценарии запрещены. Двойной клик по `.ps1` поэтому
  только открывает текст, а не запускает его. Обёртка вызывает
  `powershell -NoProfile -ExecutionPolicy Bypass -File ...`, и работает
  при любых настройках политики.
- Из `C:\projects`: `.\push-ppe.cmd -Status`, `.\push-ppe.cmd -Message "..."`.
  Из корня репозитория путь не найдётся — там скрипта нет.
- При двойном клике окно закрывается сразу после успеха (пауза в обёртке
  стоит только на ошибку). Нужен вывод на экран — запускать из терминала.
- Скрипт вызывает `git` без полного пути, ему нужен
  `C:\Program Files\Git\cmd` в `PATH` (в машинном `PATH` он есть).
- Сообщение коммита скрипт передаёт через временный файл и
  `-c i18n.commitEncoding=UTF-8`: многострочный текст с кириллицей
  ломается в аргументе командной строки.
- **На каждой машине своя копия скрипта**, и git их не синхронизирует:
  скрипт лежит вне репозитория. Правка, сделанная на одной машине, на
  другой не появится — повторять вручную. Так и вышло с BOM: на work
  исправлено, на home копия осталась с прежним `Set-Content`.

### Если git запускает ассистент

Ограниченная среда, в которой ассистент выполняет команды, может мешать
сильнее обычной консоли. Проверено на work 4 ноября 2026:

- `git` может отсутствовать в `PATH` процесса → вызывать по полному пути
  `C:\Program Files\Git\cmd\git.exe`.
- Штатный TLS-бэкенд `schannel` падает с `SEC_E_NO_CREDENTIALS` →
  `git -c http.sslBackend=openssl ...`.
- Сохранённые креды недоступны: помощник не запускается
  (`sh.exe: couldn't create signal pipe`), поэтому push требует разового
  расширения прав на команду. Анонимный `ls-remote` к публичному
  репозиторию работает и без этого.
- Токен с правом `repo` сохраняется через окно входа GCM как запись
  `git:https://github.com`; повторно вводить его не нужно. Проверено:
  push в GitHub проходит.

**Репозиторий вне OneDrive — намеренно.** Раньше он лежал в синхронизируемой
папке, и `.git` мог попасть в момент записи: это даёт битые объекты и
конфликтные копии вроде `index (1).lock`. Резервная копия и синхронизация —
на GitHub, OneDrive для этого не нужен.
